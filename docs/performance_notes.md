# R01 M1 Pro 성능 측정

현재 상태: R01의 A10분/B20분 측정과 저장 자료 재검산을 완료했다. 수치는 [performance_m1pro.json](../data/reports/performance_m1pro.json), 다음 작업의 단일 기준은 [WORK_STATUS](WORK_STATUS.md)를 따른다.

## 고정 조건과 부하 선택

Godot 4.7.2 / Forward+ / Metal을 편집 화면 밖의 별도 runtime-only 사본에서 실행한다. 설치된 Standard 편집기 포함 바이너리를 게임 모드로 사용하며, R03의 release 앱과 구분한다. 네트워크를 차단하고 원본 지도·Python 가상환경·프로젝트의 `.godot` 캐시를 복사하지 않는다. 시스템 전체 드라이버/셰이더 캐시는 지우지 않으므로 완전한 최초 GPU 실행으로 부르지 않는다.

| 조건 | A | B |
|---|---|---|
| 장면 | 도시 랜드마크 | 같은 도시 + 현재 V0 움직임 |
| 보행자 / 차량 | 0 / 0 | 2 / 2 |
| 실제 출력 이미지 | 1920 × 1080 | 동일 |
| 3D 해상도 배율 | 1.0 | 동일 |
| 렌더러 / 조명 / 그림자 / 시야 | 기존 Forward+ 설정 | 동일 |
| 준비 | 30초에 카메라 경로 한 번 | 동일 |
| 측정 | 같은 300초 경로 2회 | 같은 경로 4회, 총20분 |
| 입력 / 캐릭터 / 안내 UI | 입력 해제·시작점 정지·안내 숨김 | 동일 |

V06의 B 12명/4대와 선택 C 24명/8대는 제안이다. 현재 구현은 각각 고유 원천 선에 묶인 2명/2대이며, 더 많은 개체를 안전하게 합류시키는 정책은 구현하지 않았다. 검증된 기본 개체를 모두 유지한 B 2/2를 첫 버전의 측정 부하로 삼고, 제안 부하나 현실 교통량을 시험했다고 주장하지 않는다. UI를 숨긴 카메라 부하 측정이므로 최종 앱의 조작/메뉴 비용과 물리 보행은 별도로 확인한다.

## 같은 카메라 경로의 의미

N04의 최종 실제 GPU 자료에서 W04 전체 여정에 해당하는 카메라 위치·방향·FOV·near만 추출한다. 대한문 양방향·경내 순환·중화전 앞마당·시청/서울광장·돌담길의 11단계와334원문 구간을 모두 포함한다. 연속 관측 이후의 낙하/복귀 등 위치 주입은 제외한다.

약16분인 원래 여정의 실제 카메라 표본을300초에 재생한다. 표본 사이를 직선 보간하지 않고 직전 실제 위치를 사용한다. 카메라 경로·시간 배율과 조명은 A/B에서 같다. 현재 NPC/차량은 실제 시간으로 독립 이동하며, 차량의 화면 밖 반복 판정에도 측정 카메라를 연결한다. 이것은 같은 화면 부하를 비교하기 위한 별도 카메라이며, 플레이어 보행·새 화면 비율에서의 카메라 충돌을 검증한 결과가 아니다.

## 보존하는 관측과 판단 범위

실제 렌더 완료 신호 사이의 단조 시계 간격을 매 프레임 저장한다. p50/p95/p99/최대 프레임 시간과 평균 FPS, 각5분 창의 분포를 원시 자료에서 다시 계산한다. 엔진의 process/physics 시간·draw call·표시 객체·메모리 관측은 API의 의미와 단위를 함께 기록한다. 엔진 관측값은 갱신 지연이 있을 수 있으며, `TIME_PROCESS`를 CPU 전체 프레임 시간이라고 부르지 않는다.

현재 PID의 RSS와 CPU 사용률을1초 간격으로 관측하고, 측정 전후 시스템 메모리 압력·스왑·전원 연결/절전 설정을 기록한다. RSS에는 시작/준비 구간도 포함하며, 측정 구간의 추세는 별도로 해석한다. 읽을 수 없는 GPU 프레임 시간·센서 온도 등은 `null`과 이유를 남긴다. 서로 다른 메모리 종류를 더해 프로세스 사용량으로 만들지 않는다.

원시 프레임 배열은 짧은 묶음으로 파일에 저장해 시험 도구 자체의 메모리 증가를 줄인다. 원시 자료·실제1920×1080 화면·카메라 원천/추출본·코드/자산 SHA를 보존한다. 잘못된 실행의 로그와 판정은 최종 성공 자료로 덮어쓰지 않는다. 5초 smoke는 기동/API/해상도 확인용이며 정식 성능 결과가 아니다.

초기 p95≤33.3ms는 아직 제안이다. 실제 측정 결과와 느린 시점의 표시 객체/draw call·엔진 시간·A/B 차이를 근거로 R02의 채택 설정을 결정한다. 공개 API로 원인을 분리할 수 없으면 병목을 확정하지 않고 관측한 상관관계와 추가 비교를 기록한다. 발열 센서 없이20분 결과만으로 온도나 스로틀링 원인을 단정하지 않는다.

## 최종 결과와 필요한 조정

첫5초 smoke는 초기 창 설정이 프로젝트 기본1152×720으로 덮여 실제 해상도 검사에서 중단됐다. 처음 렌더된 프레임 이후에 창/뷰포트 설정을 적용하고 그 크기로 다시 렌더한 뒤 읽도록 수정했다. 재시험은 A27/B37 검사 PASS이며 정식 성능 결과와 구분한다. 저장 원시 자료의 독립 재검산 A40/B50 및 해상도/프레임 누락/시계/actor/RSS 변조6종의 관련 거부도 확인했다.

| 관측 | A0/0 | B2/2 |
|---|---:|---:|
| 실제 측정 초 / 프레임 | 600.007201 / 71,982 | 1200.003879 / 143,935 |
| 평균FPS | 119.968560 | 119.945446 |
| 프레임 p50 / p95 / p99(ms) | 8.332 / 9.952950 / 10.966190 | 8.329 / 9.613300 / 10.481 |

모든 프레임을 실제 source tick의11단계에 배정했다. 가장 느린 합산 stage p95는 A의 `court_forward`10.513650ms, B의 `stonewall_forward`9.715000ms다. 한5분창·한stage의 최대p95도10.666600/10.164050ms다. 20분 뒤 프레임 분포의 지속적인 악화는 보이지 않았다. [전 구간 재집계와 재현](../data/reports/r01/stage_analysis.json).

현재 목표를 놓치는 구간은 없다. 따라서 R02의 첫 선택은 실제 배치·충돌·표시거리·그림자·2명2대를 유지하는 것이다. 별도 GPU 프레임 시간이 없어 CPU/GPU 병목 원인을 분리하지 못했으므로 엔진 시간·draw call·실제 화면을 함께 남기는 계획 대안을 적용했다. B의 p95가 A보다 낮은 것을 개체 추가로 빨라진 결과로 설명하지 않는다. A→B 순서의 각1회이고 일반 백그라운드 작업과 캐시 상태가 달랐다.

B의5분창별 RSS중앙값은 약322.13→189.34→189.11→173.14MiB였으며 주기 관측의 최대 공백은 약1.042초다. 시스템 free 비율은53→54%, swap 사용량은5150.81→5126.81M였다. 이는 시작·종료 조회이며 연속 시스템 압력 측정은 아니다. 엔진 `MEMORY_STATIC`은약12.06MiB증가했고1Hz관측배열도포함한다. RSS감소나고정object수만으로누수없음을보증하지않는다. 측정은AC전원·lowpowermode0이었다. 온도/발열원인·CPU/GPU인과는미관측이다.

프로세스 실행→첫 프레임 로그 수신은 A1.897382/B2.106807초, 장면 생성→설정된 첫1920×1080프레임은0.907084/1.187305초였다. 두 시간은 시작점과 로그 전달 지연이 다르다. 시스템 전체 shader cache를 지우지 않았으므로 최초 설치 기동으로 부르지 않는다. 실행 자료26파일은16,500,248bytes이며 앱 크기는 R03의 실제 산출물에서 별도로 기록한다.

## 저장 자료로 재확인하기

아래 명령의A를B로 바꾸면두프로필을독립적으로재검산한다. 출력은기존파일을덮어쓰지않는새경로를사용한다.

```sh
.venv-data/bin/python tools/check_performance_evidence.py --record data/reports/r01/A.json.gz --plan data/reports/r01/A_benchmark_camera.json.gz --report data/reports/r01/A_performance.json --frame-batches data/reports/r01/A_frames.jsonl.gz --output /tmp/sim2seoul-A-recheck.json
```

원시프레임·묶음JSONL·카메라원천·보고서의SHA와정확한재계산을대조한다. [최종6종변조](../data/reports/r01/development/negative_controls/final/index.json)와[재실행](../data/reports/r01/development/negative_controls/final/replay_check.json)은동결된Bsmoke의정확한patch와원본SHA를보존하며실제엔진결함6회로확대하지않는다. `development`의최초실패/이전검사결과는최종정식자료와구분한다.

R02는기본설정의채택과가벼운설정/메뉴의기능회귀를확인한다. R03은편집기없는실제앱, R04는같은앱의기기별성공/실패/미실행판정이다. 이번카메라측정으로사람조작·물리보행·release앱·M4성능을대신하지않는다.
